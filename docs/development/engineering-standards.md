# 工程与注释规范

本规范适用于现有模块化单体，作为新增代码和评审的共同标准。已落地的自动门禁、需要人工审查的约定和尚未实施的行为改造在本文中分别标明，避免把目标能力写成当前保证。

## 语言、命名与格式

- 交流、新增文档、模块说明和业务注释默认使用中文。API 字段、类名、函数名和外部协议名称保持英文。
- Python 遵循项目 Ruff 配置，行宽 110；代码格式由 `ruff format` 统一。文件使用 UTF-8，导入顺序由 Ruff 检查。
- 使用业务含义明确的名称。布尔值说明判断对象，时间、金额和计数说明单位；无法获取的费用不要默认为“确定为零”。
- 用类型标注明确输入输出。对动态供应商响应先解析和验证，再进入内部用例；不要用大范围 `Any` 或忽略规则隐藏公共接口问题。
- 第一阶段类型门禁针对配置中列明的纯规则与边界契约；其他代码仍按原配置逐步治理，不能宣称全仓严格类型检查已经通过。

## 文档字符串与行内注释

复杂公共用例、执行入口、Provider 能力和状态转换函数必须有文档字符串。字段含义超出类型本身时，数据结构也需要说明。简单私有转换函数可使用一句说明，清晰的属性转发不必逐个写模板。

按复杂度使用以下结构，省略不适用项，不为凑齐模板填写空泛文字：

```python
"""用一句话说明业务动作和结果。

Args:
    ...: 参数含义、允许范围及前置条件。

Returns:
    返回结构、对象生命周期或部分成功语义。

Raises:
    ...: 已知失败条件，区分输入、状态和外部服务错误。

Notes:
    事务提交责任、持久化和外部副作用，以及重试、取消与恢复边界。
"""
```

行内注释解释业务原因、特殊约束和容易误用的边界。避免重复代码字面含义，也不要把某个样例通过写成所有情况的保证。

以下描述必须有对应实现和验证：配置冻结、幂等、线程安全、任意中断恢复、完整审计、独立 worker、真实质量评估。只保存配置指纹不能称完整快照；节点检查点不能等同于外部请求恰好执行一次；mock 或 stub 的 Provider 尝试数不能称真实 HTTP 调用数。

行为变化时同步更新注释。兼容实现、限制和临时策略明确写出适用范围；TODO 说明问题和预期验收，不使用没有上下文的“以后优化”。

## 模块接口与依赖

- 业务模块拥有自己的用例和规则，通过 `public.py` 或 `contracts` 暴露边界。
- 技术接口仅使用架构测试允许的路径。新实现不能导入旧 `services/core/agents/providers` 等兼容入口，也不能产生模块循环依赖。
- 领域规则依赖标准库和本模块领域代码，不直接调用数据库、HTTP、FastAPI 或 Runtime。
- `bootstrap` 负责组装默认实现；不能为每个模块复制一份配置缓存、Session 工厂、注册表或 ORM Base。
- 目前公共入口仍存在 Session/ORM 参数和惰性导出，这是兼容阶段的现状。新增接口优先使用明确类型与 DTO；存量接口迁移需要单独评估序列化、会话和兼容性。
- 模块责任人负责业务规则和公开契约，平台维护者负责技术运行机制。实际责任人由团队指定并维护，不能仅以目录名称代替评审责任。

## 事务、异常与外部调用

公共用例必须明确自己是否提交事务。现有多数业务用例接收调用方 Session，只查询、修改和 `flush`，调用方负责提交或回滚。返回的 ORM 对象可能绑定当前 Session，不能暗示其可跨线程或任意延迟使用。

SQLAlchemy Session 按单个执行上下文拥有，不跨 worker 线程共享。数据库写入与外部模型、HTTP、FFmpeg 之间的等待边界必须显式考虑；“各 worker 各有 Session”不代表事务天然短小。

对外错误使用既有错误类型和响应结构。捕获异常时保留原因，记录必要上下文；不要将失败包装为正常完成。日志和返回值不能包含密钥、Authorization、完整环境变量或未脱敏供应商请求头。

重试规范至少说明：允许重试的错误、最大尝试数、退避、repair/fallback 是否占预算、重复写入和重复计费风险。无法保证幂等时直接说明。取消还应区分“阻止后续节点”和“中断已发出的外部请求”。

## 状态与版本契约

新增或改变阶段状态时，在设计说明中维护转换表：

| 当前状态 | 操作与前置条件 | 成功结果 | 部分成功或失败 | 是否允许重试/继续 |
| --- | --- | --- | --- | --- |
| 待执行 | 所需输入已经满足 | 按实际阶段定义 | 保留失败原因 | 说明外部副作用和重复处理规则 |
| 待审核 | 审核记录仍未处理 | 通过并应用明确范围的标记 | 驳回及后续重新进入策略 | 说明审核对应的产物版本 |

表格是后续改造的设计要求，不表示现有状态枚举已经统一。当前媒体流程有部分成功结果，审核也未完整冻结产物快照；本轮仅校准说明，不修改既有推进和批准行为。

涉及版本的用例写明：何时新增版本、如何选择 canonical、通过哪一版、生成新版本是否使旧批准失效。返回普通 `dict` 的存量阶段结果需要逐步收敛为明确契约，迁移时保持 API 兼容或提供版本策略。

## 测试与质量门禁

本地和 CI 使用同一个 `scripts/checks/quality_gate.py`。它只检查代码质量与架构，不调用真实模型；完整后端回归和独立 smoke 按[测试说明](../testing/README.md)执行。

测试断言围绕输入输出、状态、版本、隔离、错误和资源生命周期。业务变更增加能暴露该问题的回归；格式和注释整理使用现有回归及执行结构对照，不增加复述实现的测试。

测试数据库、存储和环境必须隔离。自动检查使用 mock/stub；真实模型验收独立报告供应商、模型、来源证据、样例范围和费用相关信息。不能把 mock 产物或调用次数当成真实生成质量。

锁文件变更与依赖声明同步审查。开发和 Python CI 使用 `uv sync --frozen --extra dev`；不能静默重新解析依赖。其他交付路径的依赖锁定在完成独立改造和验收前不得宣称一致。

## 运行、观测与评审

- 默认单实例。启动前检查现有服务，端口冲突不能自动成为另开实例的理由。
- 网页测试创建的进程由测试负责清理，异常路径也执行清理；不停止非本次创建的服务。
- 新增执行日志应包含适用的 project/task/workflow/agent/request 关联标识、耗时和结果。现有日志尚未全部结构化，审计持久化也有外层事务影响，需避免过强承诺。
- 对外部署明确可信身份入口、授权、代理头处理、生产配置、readiness/liveness 和停止策略。开发身份头不能直接当成完成的外部用户鉴权。
- 评审检查行为、契约、兼容性、相关测试、资源清理和文档。数据库变更还需要升级与失败处理方案。

## 后续行为与交付任务

以下任务独立实施、独立验收，本轮规范与注释整理不将它们标为完成：

| 任务 | 需要明确的决定 | 最低验收证据 |
| --- | --- | --- |
| 阶段结果与状态 | 部分成功能否推进、占位产物能否正式导出 | 全成功/部分失败/全失败/取消的状态与产物回归 |
| 视频引用契约 | 手工选择和自动生成分别保存的 generation/asset 标识如何统一 | 选择版本后播放、合成、导出及旧数据兼容验证 |
| 审核版本 | 待审时固定哪些版本，新生成如何影响批准 | 待审后修改、批准后重生成、重复审核的交叉测试 |
| 事务与恢复 | 外部调用前后提交边界、幂等键、失败审计持久性 | 外部成功后提交失败、进程中断恢复、重复执行验证 |
| 数据库迁移 | 迁移工具、升级兼容、备份与恢复策略 | 上一版数据升级、失败保护、恢复演练 |
| 交付依赖锁定 | Docker/Windows 安装器使用同一验证过的依赖解析 | 干净环境构建安装、产物和锁定版本对照 |
| 生产身份与运行 | 可信网关或应用鉴权、线程池支持边界、停机和单实例机制 | 身份伪造拒绝、重复启动、运行中停机与重启对账 |
| 持续检查启用 | 实际托管平台、分支规则与维护责任人 | 主线/PR 的成功运行记录与合并条件配置 |

每个任务应先梳理实际调用链，再选择可独立验证的改动；没有完成相应证据前，文档保持现状说明。
